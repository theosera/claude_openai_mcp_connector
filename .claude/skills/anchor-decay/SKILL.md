# anchor-decay — 行番号はキャッシュであって参照ではない

行番号は書いた瞬間のリビジョンに対する**キャッシュ**である。参照として残したければ
**文字列 (grep パターン)** にする。「`94d4da9` 時点の :119」のように、キャッシュには
必ずリビジョンを添える。

## 規則

1. **記録は grep パターンを主、行番号を従にする。** 行番号だけの記録は、読み手に
   「まだ合っている」ことの検証手段を渡さない。
2. **腐ったかの判定は 3 段で狭まる — 決めるのは最後の 1 つだけ**:
   「main が動いたか」(不十分) → 「そのファイルが変わったか」(不十分) →
   **「その anchor より上に何行入ったか」** (これだけが決める)。
3. **腐り方は 3 種で、危険度が違う**:
   - **移動** — ずれが一定なら機械的に追える
   - **移動 + 改稿** — **最も危険**。行頭が一致するので照合に通るのに、言っていることが別
   - **消滅** — 追えない
   **今回追えたことは、次も追えることを意味しない** (削除や並べ替えが混ざれば
   ずれは一定にならない)。
4. **再取得は、記録された grep を新リビジョンに対して回す。** 行番号を写し直すのではなく、
   その機会に文字列 anchor へ移す。

## 事故録 (すべて実測 / 2026-08-17、対象リポの PR #128 = `6897747` → `94d4da9`)

- **1 本の PR の中に反例が 3 つ同時にあった**:
  - `src/` = **0 行** (anchor 5 本すべて生存 — 「main が動いたから腐る」の反例)
  - `docs/ROADMAP.md` = **+118 行だが影響 0** (3 ハンクとも 1304 行目以降 —
    「変わったファイルは危ない」の反例)
  - `docs/threat-model.md` = **+52 行のうち 80 行目の +10 だけが効いた** (残り 42 行は
    該当行より下 — 「差分が大きいほど危ない」の反例)
- **旧 `:119` / `:138` は新 `:129` / `:148` に「byte 一致で存在」と一度報告された** — 後の
  全量比較で**移動と同時に改稿されていた**ことが判明 (285→331 / 755→673 chars。第 3 列が
  `—` から実際の記述に変わっていた)。**「移動 + 改稿」の実例が「byte 一致」報告の中に
  隠れていた** (→ 全量比較は `measurement-scope`)。
- **`ROADMAP.md:369` / `:755` は消滅** — 追えなかった側の実例。
- **粒度の事故**: 「原因は +52 行」とだけ書くと、次の読み手が「52 行入ったファイルは危ない」
  と一般化し、+118 行で影響 0 の ROADMAP を説明できなくなる。効いた行数 (+10) と
  効かなかった行数 (+42) を分けて書く。

## アンチパターン

- 行番号だけの申し送り (受け手が検証できない → `handoff-block-integrity`)
- 「main が動いていないから生きている」という生存理由の記録 (動いた瞬間に判定不能になる。
  正しい理由は「その anchor より上に何も入っていないから」)
- ずれの一定性を確認せずに「+N すれば追える」と書く
